# Print Shop Tycoon

Cosy isometric 3D printing business sim in Godot 4.7 (GDScript). `docs/GDD.md` is the source of truth for design and the phased build plan. Read the section for the current phase before starting work.

## Working rules

- One phase at a time, each on its own branch (`phase-N-short-name`). Don't start a phase until the previous one meets its "done when".
- Don't build systems from later phases early. Stub them if something needs to exist.
- Tick the checkboxes in `docs/GDD.md` section 5 as tasks land.
- Content is data driven: printers, filaments, products, parts, marketplaces and contracts live in `data/*.json`, never hard coded. Schemas are documented in `docs/data_schemas.md`; update it when a table changes.
- Simulation logic (economy, wear, failures) stays separate from scenes and visuals: plain `RefCounted` classes with no node dependencies, so it can be run and tested headless.
- Parody names only for brands and marketplaces. No real brands.
- UK English in names and text (colour, organiser, licence).

## Layout

- `docs/` GDD, data schemas, balancing notes (ignored by Godot)
- `docs/design_data/` content designed ahead of the build (660 products, 38 printers, filaments, parts, presets, failures, shipping). Reference only: the game loads `data/`, and each phase imports what it needs from here. Read its README before adding content or product models
- `tools/generators/` Blender Python asset generators, one per asset family (ignored by Godot)
- `tools/previews/` preview renders from the generators (git ignored)
- `assets/` generated `.glb` models, palette texture, shared material
- `data/` JSON content tables
- `scenes/` garage, small unit (`scenes/unit/`), workshop (`scenes/workshop/`) and factory (`scenes/factory/`); `scenes/dev/` for test scenes
- `scripts/` gameplay code; `scripts/dev/` for headless tools, `scripts/import/` for import scripts

## Tools

Neither tool is on PATH. Run from the repo root.

- `godot` below is `S:\Godot Games\godot-4.7.1\Godot_v4.7.1-stable_win64_console.exe`
- `blender` below is `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe` (not `blender-launcher.exe`, which hides console output)

```
godot --headless --path . --import                                        # import new or changed assets
godot --headless --path . --script res://scripts/dev/validate_data.gd     # check data tables
godot --headless --path . --script res://scripts/dev/build_palette.gd     # rebuild palette.png from data/palette.json
godot --headless --path . --script res://scripts/dev/import_products.gd   # rebuild data/products.json from the design catalogue
godot --path . res://scenes/garage/garage.tscn -- --shot=tools/previews/godot_garage.png   # screenshot any scene, then quit
```

`--shot=<png>` and `--shot-delay=<seconds>` work on every scene (the `DevShot` autoload, `scripts/dev/dev_shot.gd`). Use them to look at changes in engine rather than assuming they worked. Dev scenes: `scenes/dev/asset_preview.tscn` (every model in a grid) and `scenes/dev/character_preview.tscn` (one character per animation).

Checking gameplay without clicking: the `DevAutoplay` autoload (`scripts/dev/dev_autoplay.gd`) drives the real action menus from the command line, and combines with `--shot-times` for screenshots along the way.

```
godot --headless --path . --script res://scripts/dev/run_tests.gd    # unit tests for simulation classes
godot --headless --path . --script res://scripts/dev/balance_report.gd   # play the garage, then on into the small unit, many times and report the economy (see docs/balance_notes.md)
godot --path . res://scenes/garage/garage.tscn -- --time-scale=2 "--autoplay=call>place_supplier_order({\"printers\":{\"plodder_mini\":1},\"spools\":{\"red\":1}});wait>80;Delivery: 1 spool>Unpack;Delivery: Printer>Unpack;Plodder Mini>Load filament>Red;Plodder Mini>Print...;on>print_dialog>choose(\"cable_management_clips_x12\",\"standard\");shot>tools/previews/play.png;quit"
```

Runs with `--autoplay` or `--shot` neither load nor write the save game, so they always start fresh and never touch a real one. Add `--save=user://some_test.json` to a run to have it load and save that file instead; `on>world_save>save_now()` saves on the spot.

For a close look in a shot, `zoom>Plodder Mini>1.8` centres the camera on an object and sets the view to that many metres tall. The character often stands in the way: `on>player>walk_to(Vector3(1.5,0,1.5))` sends them off first.

To wear a part without printing for hours, use `on>printer>wear.damage(\"nozzle\",0.9)`. To see a particular failure, put `call>set(\"force_failure\",\"spaghetti\")` before the print step: the next print is certain to hit it.

## Gameplay architecture

Control is semi-autonomous: the player clicks an object, picks from its action list, and the character does the whole task. Tasks queue.

- `Interactable` (`scripts/interaction/`) is the base for anything clickable. Subclasses override `get_actions(agent)` to return `Action`s; each Action's `run` is a coroutine that drives the character. The script goes straight on the instanced model node in the scene, with `display_name` and `stand_offset` set there. It builds its own click collider from its meshes.
- An Action with `immediate` set runs when picked instead of being queued. It is for opening a dialog (the printer's "Print..." opens `PrintDialog`, which then queues the real task).
- A print's fate is decided when it starts: `Game.roll_print` uses `PrintRisk` (`scripts/sim/`) with `data/presets.json` and `data/failures.json`. A ruined print leaves a `FailedPrint` on the plate until the character clears it; a spoiled one finishes as a flawed `PrintedItem`.
- What is in a parcel follows the order: packing records the item's durability, quality and whether it is flawed on the `Marketplace.Order`, with how it was sent (`order.shipping`). `Marketplace.deliver` later decides if it is lost, arrives broken, is sent back or is reviewed, and `Game` puts refunds through the bank. The seller rating scales demand.
- `Shipping` (`scripts/sim/`, `Game.shipping`) has the rules of packaging and postage, from `data/packaging.json` and `data/couriers.json`: the parcel band a design falls in, what it fits in, what a courier's service charges, and the `terms` that follow an order. Each design goes out in one kind of packaging (`Game.packaging_of`, chosen on its listing: `Game.set_packaging_choice`) and each marketplace sends by one service (`Game.service_of`, chosen in its app: `Game.set_service`). In a dev run: `call>set_packaging_choice(\"desk_nameplate\",\"poly_mailer_bag\")`.
- Orders are packed at the `PackingStation` (`scripts/interaction/`, group `packing_station`), not the workbench: the packaging is laid open on its `pack_spot`, the item goes in and the flaps shut (`Parcel.set_open`, `Parcel.close`). Piles of each kind in stock show in its `stock_slot_*` markers. In a dev run: `Packing station>Pack order>#CR-1001`.
- Storage grows two ways (`StorageRules`, `scripts/sim/`, `Game.storage`). Shelving and racks are bought as fittings (`data/fittings.json`, the supplier basket's `fittings`) up to the premises' `shelf_units` and `rack_units`. One arrives flat packed, and unpacking it starts the `Placer` (`scripts/interaction/placer.gd`): a see-through copy follows the mouse, green where it fits, and a click sets the character to putting it up there. It becomes a `FittingUnit`, which only adds its spaces to the scene's one `StorageShelf` or `FilamentRack`: use `shelf.spot(what)` and `rack.spot(...)` for where to walk to, never the shelf itself. A move takes bought units down and re-delivers them. In a dev run: `on>delivery_box>place_at(Transform3D(Basis(), Vector3(0.9, 0, 0.3)))`.
- Printer racks (and a plain bench) are fittings of kind `bench`: the row's `printer_spots` become more places on the one `Workbench`, which owns every printer and every place (`install_printer`, `remove_printer`, `move_printer`, `next_place()` for where to stand), up to the premises' `max_printers` in all. The benches a place comes with can be taken out for good once empty (`remove_bench`, from the bench's menu) to make room for racks: a print farm's plain benches are in the `spare_bench` group and are clicked through a `BenchProxy`, and the `Workbench` node itself only goes out of sight, since it still owns the printers. A printer's "Move it" menu carries it to another bench or rack. A printer's "Sell or scrap it" menu boxes it at the packing station for the courier (`Parcel.create_resale`, paid by `StorageRules.resale_value` from its parts' health, the `resale` settings) or bins it. A task that removes its own node must not free it until its last line, or the character is left waiting for ever.
- A print of a bin design (the `storage_bins` settings) can be put to use from the shelving's Storage bins menu. It becomes a `StorageBin` (`scripts/items/`): one space holding several prints, by size. Count room for prints with `shelf.room_for(product)`; `free_slots()` is only the spaces with nothing in them. A print goes in a bin already holding its design, then any bin with room, then an empty space; a bin design never goes inside a bin, and the printer offers to collect one "for the workshop" (`shelf.store_as_bin`). Clicking the shelving opens `ShelfDialog` (`scripts/ui/shelf_dialog.gd`) instead of a menu (an Interactable with `wants_panel()` and `open_panel()` does), where everything is laid out a space to a tile and tidied by dragging. In a dev run: `on>print_storage>open_panel()`, `on>print_storage>move_into_bin(_loose(), bins()[0])`.
- The `FinishingBench` (`scripts/interaction/`) takes a print off the shelf, plays the blowtorch over it and puts it back a point of quality better (`PrintedItem.finish`, once each; the `finishing` settings). In a dev run: `Finishing bench>Finish Cable`.
- Each printer has a `PrinterWear` (`scripts/sim/`): part health drops with print hours, worn parts add risk, and a part that runs out stops the print and the printer. Spares are `SparePart`s on the shelving, bought from the shop's Spare parts tab and fitted from the printer's Parts menu. Each part and kit has its own model (`model` in its row, built by `tools/generators/parts.py` into `assets/models/parts/`, found with `GameData.part_model(row)`); a multicolour unit waits in a plain box and has a model of its own for when it is on the printer. Each dryer has its own model too.
- Each printer also has a `PrinterMods` (`scripts/sim/`): the upgrades fitted to it from `data/upgrades.json`, which grant capabilities, scale failures, print time and wear. Kits are bought and stored like spare parts (the supplier basket's `parts` takes either; `GameData.kit(id)` finds the row) and fitted from the printer's Upgrades menu.
- A multicolour unit is an upgrade whose row has a `multicolour` block (`PrinterMods.unit()`). Fitting one puts the unit's model on the printer's `unit_mount` marker and swaps the printer's one spool for a slot per spool: `PrinterStation.spools` has an entry per slot, null where empty, and `spool` is just the first one loaded. A print draws on one slot per colour (`print_plan`, `default_slots`); the print dialog lets the player pick them, or print a multicolour design in one colour. `Multicolour` (`scripts/sim/`) has the rules: shares of filament, colour changes, purge waste (more between dark and light), swap time and jams. A `PrintedItem` has `colours`, one per part; printed in fewer than its design has, it is "plain" and sells for less (the `multicolour` toggle in `data/presets.json`). A second unit of the same kind links to the first (`PrinterMods.linked`), stacked on its `link_mount` marker, and adds its slots.
- A print can be a batch of copies (`PrintRisk.copies` says how many fit; the `batch_plate` toggle caps it and sets the time saved). `PrinterStation.item` is the first copy and `extras` the rest: they share one fate, the colour changes happen once for all of them, and they are collected in one trip. In a dev run: `on>print_dialog>choose(\"desk_nameplate\",\"standard\",[],4)`.
- Printers differ by data alone (`data/printers.json`): speed, reliability, bed size (`PrintRisk.fits`), built-in capabilities and which model file they use. `motion` picks the print animation in `PrinterStation` (a bed slinger's gantry climbs; a core XY's bed sinks). Each has its own model: a variant named for it in `tools/generators/printers.py`, built to `printer_<id>.glb`. The model's `plate_corner` marker tells `PrinterStation` how big the plate is, which sets how far the head and bed travel and how a batch is laid out. A new printer needs a row, a variant and a manifest entry.
- Resin printers are printers of `kind` "resin" and resins are filaments with `process` "resin", so they go through everything a spool does: bought as "resin:stone" keys, racked, loaded and tracked by the gram, but drawn as a bottle (`container`). A resin printer has its own parts (film, screen, vat) and its own failures (a failure's `process`), and what comes off it has to be washed and cured, which is extra time on the Collect task (`post_minutes`). A printer row with `auto_eject` (the belt printer) clears its own plate without the upgrade.
- `FilamentRules` (`scripts/sim/`) decides what prints in what: a printer's temperature, enclosure and direct drive against the filament's needs, and a design's `allowed_filaments` against the filament's id or family. Spools are named in baskets and deliveries by "material:colour" keys.
- There are several marketplaces: `Game.markets` by id (`Game.market` is the first), each a `Marketplace` with its own listings, orders, reviews and rating. Use `Game.open_orders()` and `Game.market_of(order)` rather than assuming one. One app script (`app_craftsy.gd`) serves them all; its entry in `PcScreen.APPS` names the `market`. `Trends` (`Game.trends`) puts one product category in demand and one out, and tells every marketplace.
- `Stockroom` (`scripts/sim/`, `Game.stock`) holds a reorder rule for each thing the business uses up: spools, spare parts and mailer boxes, by key ("spool:pla:red", "part:<id>", "packaging"). From tier 3, `Game.restock` runs every few game minutes: it counts what is on the premises and on its way (`Game.stock_levels`) and orders whatever a rule says has run low, if there is cash and room. The Stockroom app sets the rules. In a dev run: `call>set_stock_rule(\"spool:pla:red\",true,1,2)`.
- `Contracts` (`scripts/sim/`, `Game.contracts`) is the B2B work: from tier 3 the clients in `data/contracts.json` send enquiries to the Inbox app for a batch of a design the business owns, or one the client supplies (`contract_only` products, printable only while their contract runs: `Game.printable_designs()`). Accepted, a contract has a spec (filament, colour, finish, strength) and a deadline at a courier collection. The packing station's "Send to a client" crates whatever on the shelf meets the spec (`StorageShelf.items_for`); a crate is a `Parcel` with a contract id, and counts when the courier takes it. The last one pays, less a share for each day late. In a dev run: `call>contracts.offer(clock.minutes,rng,owned_designs,3)` makes an enquiry and `call>accept_contract(contracts.offers()[0])` takes it.
- `Staff` (`scripts/sim/`, `Game.staff`) is the team: roles, shifts, wages and each day's applicants, from `data/staff.json`, hired in the Rota app. A member of staff on shift is an `Agent` like the player's (in the `staff` group, not `player`), brought in by the scene's `StaffRoom` node with a `Worker` on it. A Worker picks its own tasks from the same action lists the player sees: an `Action` marked `for_duty(&"collect")` is one staff with that duty may take, so give new routine tasks a duty and add it to a role. Workers claim the object they are working on, and stop starting tasks while `WorldSave.wants_quiet()`, because a save needs everybody between tasks at once. A printer's "Print ... again" restarts its last job; with `repeat` on, an operator does it unasked. In a dev run: `call>hire_staff(0)`, and mind the clock, since staff go home at the end of their shift.
- Automation is two upgrades from tier 4. An auto-eject plate (`auto_eject` block) throws a finished print off the plate into a tray beside the printer (`PrinterStation.tray`), and lets a printer with `repeat` on restart itself (`_run_itself`). The overhead conveyor (`fixture: "conveyor"`) is fitted once to the building from the `Conveyor` controls in the factory scene; ejected prints then ride it to the shelving instead. Failed prints always need a person. In a dev run: `on>conveyor>install()`.
- `Events` (`scripts/sim/`, `Game.events`) starts something from `data/events.json` every few days: a design going viral or undercut (`Marketplace.boost`), a filament shortage (`Supplier.price_multipliers`), a power cut (`PrinterStation.power_cut`) or a client going bust (`Contracts.bust`). Lasting ones show in the Inbox. `Milestones` (`Game.milestones`) marks the rows of `data/milestones.json` as their figure in `Game.stats` is reached, and the Stats app lists them. In a dev run: `call>_begin_event(events.start(\"power_cut\",clock.minutes,rng,_event_candidates()))`.
- Injection moulding is the endgame: `Moulding` (`scripts/sim/`) has the rules and `MouldingMachine` (`scripts/interaction/`, on the marked bay in the factory scene) is the machine, an upgrade with `fixture: "moulder"`. A design in one colour needs a mould ordered first (dear, and days to arrive); then a batch turns pellets into a hundred copies for pennies. What it makes is a count in its output bin, by design and colour, until it is crated for a contract (a moulded part meets any material in a spec) or carried to the shelving as ordinary `PrintedItem`s. In a dev run: `on>moulder>install()`.
- `DesignStudio` (`scripts/sim/`, `Game.studio`) holds the business's own designs: versions, quality, hidden faults and skill. The Design Lab queues the work as a task at the PC (`Computer.design_action`); the marketplace is told which designs are own (`own_appeal`) so they owe no royalty and sell by their quality. In a dev run: `call>finish_design(\"phone_stand\")`.
- Spools carry `moisture`, which rises in the open by the rules in `Moisture` (`scripts/sim/`) and adds to print risk once wet. A `FilamentDryer` on the scene's `DryerSpot` takes it back out. To wet a spool in a dev run: `on>filament_rack>spools()[0].set(\"moisture\",0.8)`.
- `Game.tier` (1 garage to 4 factory) gates what the shops sell through `Game.unlocked(row)`. It comes from the premises (`data/premises.json`, `Game.premises`). The player moves from the Roomier app: `WorldSave.move` pays, captures the world and hands it to the new premises' scene, which rebuilds it. A scene started with a save from other premises redirects the same way. Start a dev run elsewhere with `--premises=small_unit`, `--premises=workshop` or `--premises=factory`, or just at a tier with `--tier=2`. A place with several benches (the workshop's print farm) still has one `Workbench`: its `printer_spots` reach onto the other benches, which are plain furniture.
- `Agent` (`scripts/character/agent.gd`, `scenes/characters/player.tscn`) owns the task queue, for the player's character and for each member of staff. Task code is a plain sequence of awaits: `go_to()`, `reach(callable)`, `work(game_minutes)`, `carry()`, `release()`, `sit()`. A task must re-check its preconditions when it starts, because the world may have changed while it was queued.
- `InteractionController` handles hover, the popup menu and floor clicks. `Hud` shows the current task and queue, with the to-do note (`TodoNote`, also on the PC desktop) beneath. `Advice` (`scripts/game/advice.gd`) decides what is on it; give each new thing to do a hint a non printer owner could follow.
- `PrinterBadges` (in the HUD) floats a status badge over each printer. Messages go through `Game.notify(text, tone)`; give bad news `&"bad"` and good news `&"good"` so the toast is tinted.
- `DayNight` (`scripts/world/day_night.gd`, a node in the scene) sets the sun, ambient light, backdrop, lamps and window light from the game clock. It is only for looks. To see a time of day in a dev run: `call>clock.set(\"minutes\",1380.0)`.
- `Surroundings` (`scripts/world/surroundings.gd`) goes on the outdoor model instanced in each premises scene (`assets/models/surroundings/`, one per premises from `tools/generators/outdoors.py`). It lights the model's `glow_*` meshes and `lamp_*` markers after dark using `DayNight.darkness(hour)`, runs traffic between the `lane_<n>_start` and `_end` markers, and sends a van to `kerb_stop` on `Game.courier_arrived`. It is only for looks. A new premises needs a layout in the generator's `VARIANTS`.
- `FloorGrid` is the navigation: an A* grid, with every node in the `obstacle` group blocking the cells under it. Add floor-standing furniture to that group. No baking.
- Items are nodes that get reparented between slot markers, the character's `carry_socket` and printer mounts (`Spool`, `PrintedItem`, `SparePart` in `scripts/items/`). Printed items use the tint material and take their filament's colour.
- Objects find each other through groups (`filament_rack`, `print_storage`, `floor_grid`, `player`), not hard-wired paths.
- The rules of the business live in `scripts/sim/` as plain classes with no node dependencies (`GameClock`, `Bank`, `Marketplace`, `Supplier`, plus `PrintJob`). Every one has tests in `scripts/dev/run_tests.gd`; add tests when adding rules.
- The `Game` autoload (`scripts/game/game.gd`) owns those objects, advances them each frame and emits `changed`, `notified`, `delivery_arrived` and `courier_arrived`. Scene nodes and UI read from `Game` and call its methods; they don't keep their own copies of cash, orders or designs.
- Saving: anything with state has `save()` returning plain data and `restore(data)` (or a static `restored(data)` for things created from a save). `Game.save()` covers the business; `WorldSave` (`scripts/game/world_save.gd`, a node in the scene) gathers the world from the nodes in its `PARTS` groups, loads the save when the scene starts and saves whenever the character is between tasks. Give new stateful things both methods and, for a new kind of scene node, an entry in `PARTS`. Saves are JSON, so restore with explicit `int()`, `float()` and `StringName()` and skip ids the data tables no longer have. Bump `Game.SAVE_VERSION` when an old save can't be read.
- Game speed is `Engine.time_scale` (set through `Game.set_speed`), so walking, animation, prints and timers all follow it. Durations in data are game minutes; convert with `GameClock.to_seconds`.
- Money is GBP pence (integers) in all data, simulation and saves. Show it only through `Money.format(pence)` in `scripts/sim/money.gd`, which converts every amount the same exact way so a price shown always equals the amount charged; don't add rounding to tidy price endings. Never write a currency symbol in UI code. The player picks GBP, USD or EUR in the Settings app; `Game.set_currency` saves it to `user://settings.cfg` and emits `changed`.
- Physical stock is nodes, not counters: spools on the rack carry their own grams, finished prints and boxes of spare parts share the shelf slots, parcels sit on the outbox. Packaging is the one counted stock (`Game.packaging`, by kind), shown as piles on the packing station.
- The PC is `PcScreen` (`scripts/ui/pc/`), a full-screen "PlateOS" desktop. Each app is one script (`app_*.gd`) that rebuilds itself in `refresh()` from `Game`; register new apps in `PcScreen.APPS`. While the PC is open the character is held (`Agent.held`), so jobs queued from an app start when the player leaves the desk.

## UI look and feel

`docs/mockups/pc_screens.html` is the visual source of truth for all UI (open it in a browser). Every screen, in the PC or over the 3D view, follows it: Fredoka headings, Nunito body text, cream cards with a flat offset shadow, chunky rounded buttons, warm accent colours, dark taskbar chips. Never ship a screen in Godot's default dark theme, even as a placeholder.

- Build UI in code from `Ui` (`scripts/ui/ui.gd`): colour constants, `Ui.text` / `Ui.title`, `Ui.card`, `Ui.box`, `Ui.button`, `Ui.pill`, `Ui.bar`, `Ui.icon`, `Ui.hbox` / `Ui.vbox`. Add a helper there rather than styling a one-off.
- Set `Ui.theme()` on the top control of each screen and on popup menus.
- A picture of a thing in a shop or a list is its real model: `ModelPicture` (`scripts/ui/model_picture.gd`) renders it once from the game's camera angle and shares the texture, filling in as pictures scroll into view. Use `ModelPicture.of_printer(spec, pixels)`, `ModelPicture.of_product(product, pixels)` or `ModelPicture.create(scene_path, pixels)` rather than drawing a stand-in.
- Icons are white line SVGs in `assets/ui/icons/`, tinted when used. Fonts are in `assets/fonts/` (see the README there about the licence files needed before release).
- The base window is 1600 x 900. Lay screens out with containers so they stretch, not fixed positions.
- Where a mock-up shows something from a later phase (reviews, part health, upgrades, print settings), leave it out or show an honest "not yet" state. Don't fill it with fake data.

## Art pipeline

- Low poly, flat shaded, warm. Every asset is coloured from the shared palette: `data/palette.json` is the source, `assets/palette/palette.png` is built from it. Append new colours rather than reordering, because cell position is baked into model UVs.
- Generators are seeded, parameterised Blender Python scripts built on `tools/generators/common.py`. Same seed and parameters must give the same asset.
- Units are metres, origin at the centre of the asset's base. The front of an asset faces Blender -Y, which is +Z in Godot.
- Parts that move in game (printer bed, gantry and toolhead, roller door, character limbs) are separate objects with their origin on the pivot. Attachment points are empties ("markers") such as `plate`, `spool_mount`, `spool_slot_1`, `carry_socket`. They import as named nodes, so gameplay code finds them by name.
- `tools/generators/manifest.json` lists every asset with its generator and arguments. Add new assets there, not as one-off commands, so everything can be rebuilt.
- The game looks from the south-east (Blender +X, -Y), so only the south and east faces of scenery show, and anything tall to the south or east of a room must stand at least its own height away or it covers the floor. `scenes/dev/asset_preview.tscn` leaves out `assets/models/surroundings/`; check those in their premises scene, zoomed out.
- A product made in several colours is several meshes: the main one, plus a child mesh named `colour_2`, `colour_3` and so on for each further colour, all in the tint material. The game tints each with the colour of the spool that printed it. They are built by `tools/generators/prints_multicolour.py` and the `prints_mc_*.py` files beside it (one per group of categories), where each variant gets a `Parts` with a builder per colour. `preview_prints.py -- --module prints_mc_play --sheet play` shows a whole file with the colours apart, and the data validator fails a model whose meshes don't match its design's `colour_count`.
- The character is short and chunky: about 1.6 m with a head a third of that, hips at 0.47 m, shoulders at 0.94 m. Furniture it uses is sized to match: chair seat at 0.4 m, desk top at 0.7 m, workbench at 0.9 m. Body parts are rounded (capsule limbs, 2 to 3 segment bevels) to match the props. To judge a change against the furniture before importing, run `tools/generators/preview_character.py`, which renders front and three-quarter views beside the desk and chair.
- Characters are animated in code, not with clips: `scripts/character/character_rig.gd` rotates the limb pivots (idle, walk, sit, plus carrying and a one-shot reach).
- Generators give meshes a placeholder material named `palette_flat`. On import, `scripts/import/palette_post_import.gd` (set as the default scene import script in `project.godot`) swaps it for the shared `assets/materials/palette_flat.tres`.
- The loop for every asset: run the generator, look at the preview PNG in `tools/previews/`, fix and rerun until it looks right, then import into Godot and check it in `scenes/dev/asset_preview.tscn`. Never import an asset without checking its preview.

```
blender --background --factory-startup --python tools/generators/build_all.py                    # rebuild everything in the manifest (about 10 s)
blender --background --factory-startup --python tools/generators/build_all.py -- --only printer  # only outputs whose path contains "printer"
blender --background --factory-startup --python tools/generators/boxes.py -- --seed 1 --variant closed --out assets/models/props/box_closed_01.glb
```

## GDScript conventions

- Static typing everywhere (typed vars, parameters and return types).
- `snake_case` files, functions and variables; `PascalCase` classes and nodes; `UPPER_SNAKE` constants.
- Tabs for indentation. `##` doc comment at the top of each script saying what it is for.
